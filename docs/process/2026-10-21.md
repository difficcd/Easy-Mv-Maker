# Process cycle 2 — 2026-10-21: an inspection

Cycle 1 measured the process. This one inspects the product, the way an outside reviewer would:
go through it against a checklist, rate what is wrong, then fix the worst first through the
normal path - a branch, a test where the finding is a defect, a PR, CI - and write down each
round before starting the next. It loops until what is left is either small or needs a decision
only the owner can make.

The checklist is the four attributes of good software the project's own review set as targets
(maintainability, dependability and security, efficiency, acceptability), with one question
added that the earlier cycle taught: **does the documentation say what is actually true?**

Every finding below rests on a measurement, not an impression, and the command that produced it
is given so it can be rerun.

## Inspection

### Findings

| # | severity | attribute | finding |
|---|---|---|---|
| F1 | high | dependability | **Half the code is never run by a test.** 67 of 150 source files, 10,719 of 23,121 lines (46.4%), are not loaded by any unit test: all of `hooks/`, all of `ui/`, `App.tsx`, `tools/`. The headline coverage of 96.8% is coverage of the other half. And `App.tsx`, untested, is where cycle 1 found the defects land - 63 fix-touches against 11 for the next file. |
| F2 | high | security | **Eight known-vulnerable dependencies, five with a fix nobody applied** - one critical (`proxy-addr`, IP spoofing), three high (`follow-redirects`, `brace-expansion`, `@xmldom/xmldom`), one moderate (`qs`). Dependabot was opening weekly PRs, which reads as covered, but those are *version* updates to the packages `package.json` names. These are transitive. Vulnerability alerts were off, and so were automated security fixes. |
| F3 | medium-high | security, docs | **The threat model in SECURITY.md is not the one the app runs under.** It says the API binds to loopback, so "anyone on your machine can read your projects". But `npm run dev` serves on the LAN (for the tablet) and proxies `/api` to that loopback server - so anyone on the same Wi-Fi can read, overwrite and delete projects, unauthenticated, in the default workflow. |
| F4 | medium | dependability, process | **The local gate was not running against what CI runs.** After a dependency PR merged, the working copy kept the old packages (`eslint@10.10.0` where the lockfile says `^10.12.0`). `npm run check` passed locally on a different toolchain from the one CI installs. |
| F5 | low | security | **Server errors are sent to the client verbatim** - `res.status(500).json({ error: String(e) })` in nine handlers - which can include filesystem paths. |
| F6 | low | dependability | **Every proxied client looks like one client to the rate limiter.** It keys on `req.ip`, and through the Vite proxy every device is `127.0.0.1`, so one device's burst throttles the rest. Not exploitable for spoofing (no `trust proxy` is set, so the `proxy-addr` CVE does not reach), and harmless for one person - recorded, not fixed. |
| F7 | low | maintainability | 8 React hook dependency warnings, already pinned by the hook baseline. Known and tracked; not reopened here. |

How each was measured:

```bash
node --experimental-strip-types --experimental-test-coverage --test "test/**/*.test.js"   # F1, then diff against git ls-files src
npm audit --json                                   # F2
gh api repos/difficcd/Easy-Mv-Maker/vulnerability-alerts -i       # F2: 404 = off
gh api repos/difficcd/Easy-Mv-Maker/automated-security-fixes     # F2
grep -n "proxy\|host" vite.config.js; grep -n "HOST" server/index.js   # F3
npm ls eslint wait-on                              # F4: "invalid"
grep -n "String(e)" server/*.js                    # F5
```

### Order of work

Severity first, then cost. F2 is high and nearly free, so it goes first; F1 is high and the most
expensive, so it is started rather than finished; F3 and F5 are one change to how the server
presents itself; F4 is a guard against a mistake that was made during this very inspection.

## Rounds

### Round 1 — F2, vulnerable dependencies

**Change.** `npm audit fix`, which touched only the lockfile: no `package.json` change, no major
version. Then two things so it cannot quietly come back:

- a CI step, `npm audit --omit=dev --audit-level=high`, which fails when anything the app ships
  with has a known high or critical vulnerability. Outside `npm run check` because it needs the
  registry; dev tooling left out because its advisories concern the build machine.
- the root cause, in the repository settings: Dependabot **vulnerability alerts** and
  **automated security fixes**, both of which were off. Version updates were on, and they were
  doing their job - which was never this one.

**Verified.**

| | before | after |
|---|---|---|
| all dependencies | 8 (1 critical, 3 high, 4 moderate) | 3 moderate |
| runtime only (`--omit=dev`) | 2 (1 critical, 1 moderate) | **0** |
| vulnerability alerts / security fixes | off / off | on / on |

`npm run check` green; the API server booted on the updated Express stack and answered a GET and
a JSON POST (the `qs`/body-parser path the fix touched). The three left are in the Android build
toolchain (`@capacitor/cli` itself, and `xcode` and `uuid` under it) and the only fix npm
offers is a downgrade of `@capacitor/cli`, so they are accepted and stated here rather than
silenced.

**Effect on the finding.** Closed for runtime, guarded in CI, and the early warning is on.

### Round 2 — F3 and F5, how the server presents itself

**F5, the error text.** Nine handlers sent `String(e)`. Checked before changing anything: the
client's `apiFetch` reports only the HTTP status and never reads an error body, so for the
project and backup routes that text had one audience - whoever called the API directly. The
YouTube routes are different: the client does show their message, and "the disk is full" is
worth seeing. So `server/errors.js` turns an error's *code* into a sentence (a full disk, a
permission, a missing file), sends nothing else, and logs the whole error on the server. Tests
first: a filesystem error with a path in it must not send the path; a known code must still
produce a sentence the user can act on; a response that has already started streaming must be
logged, not answered twice.

**F3, the threat model.** Inspecting it turned up a second document wrong in a different way:

| document | said | wrong because |
|---|---|---|
| SECURITY.md | "anyone on your machine" can read projects | the dev server proxies `/api` onto the LAN |
| README (en, ko) | the API "listens on all interfaces", ":8787" is exposed | the API listens on 127.0.0.1; the exposure is the dev server's `:5175/api` |

All three now say the same true thing. And the documentation was not the only fix: the dev
server now **warns when it starts** that `/api` is on the network, and **`MV_LAN=0`** keeps it on
the machine - checked by running it both ways:

| | warning | Network URL | bound to |
|---|---|---|---|
| default | printed | shown | `::` (all interfaces) |
| `MV_LAN=0` | none | none | `::1` (loopback) |

The default is unchanged on purpose: the tablet workflow depends on it. Authentication is the
real fix and is a design decision, so it is listed under open items rather than guessed at.

**Also found while here.** README still said the dev server was on `:5173` and that "if 5173 is
taken, Vite moves to 5174, 5175..." - both untrue since #364 fixed the port at 5175 with
`strictPort`, and that PR did not update the README. A miss of exactly the kind cycle 1's
documentation rule is about; corrected here.

### Round 3 — F4, the local gate on the wrong toolchain

This one happened during the inspection itself. Dependabot's PR had merged on GitHub and been
pulled, but nobody reinstalled, so the working copy kept `eslint@10.10.0` where the lockfile says
`^10.12.0`. `npm run check` went on passing - on a different toolchain from the one CI installs
with `npm ci`. Nothing reported it, and every figure taken earlier in the session had been
measured on that stale tree; the audit in round 1 was rerun after `npm ci` for that reason.

**Change.** `scripts/deps-installed.mjs` runs first in `npm run check`: it reads `npm ls` and
fails on a package that is *invalid* (below its declared range) or *missing*, with the one
command that fixes it. An extraneous package is clutter, not a different toolchain, and passes.
First because every check after it is only meaningful on the right packages.

**Verified by reproducing it**, not only by the unit tests:

| state | result |
|---|---|
| fresh `npm ci` | passed |
| an older eslint installed without saving - the situation as it was | **failed**, naming `eslint@10.10.0` |
| `npm ci` again | passed |

### Round 4 — F1, making the coverage figure honest, and holding it

F1 is the largest finding and the most expensive to close, so this round does what is cheap and
permanent first: measure it truthfully, and stop it getting worse. Writing tests for a
2,200-line component directly is not the remedy the methodology offers; moving its logic into
tested modules is (round 5).

**The figure.** Node's coverage report lists only the files a test loaded, so an untested file is
not a 0 in the table - it is absent from it. Counting those files at their full length, the same
way Node counts a loaded one (every line, comments included, so the two halves compare):

| | lines | covered |
|---|---|---|
| files a test loads (83) | 12,319 | 11,651 (94.6%) |
| files no test loads (67) | 10,652 | 0 |
| **all of src/** | **22,971** | **11,651 — 50.72%** |

against a headline of 96.8%. The untested half, by size: `hooks/` 4,109 lines, `ui/` 3,696,
`App.tsx` 2,198, then small pieces of `canvas/`, `tools/`, `main.tsx`, `export/`, `core/`.

**Change.** `scripts/coverage-ratchet.mjs` runs the suite with coverage, computes that figure and
fails if it falls below the pinned baseline (`scripts/coverage-baseline.json`, 50.72%). It replaces
`npm test` in `npm run check` - coverage cost nothing measurable here (7s with or without), so the
suite still runs once. `UPDATE=1` raises the baseline when the figure has risen, as the hook
baseline does.

A ratchet, not a target: it does not demand a number, it demands that untested code stop
accumulating. That is the precise shape of the problem the review described - structure getting
worse as features are added - applied to tests.

**Verified.** Its own tests include the case that defines the finding (leave an untested App out
and a layout reads 88%; counted in, 22%). And a drop was simulated: an untested 300-line file
added, figure 50.72% → 50.07%, **failed**, naming `src/core/` as where the untested lines grew.

**Also: the gate's output.** Running the suite through the ratchet showed what the gate had been
printing all along - TAP, one line per subtest, **8,186 lines** for a passing run, in which the
line that matters was impossible to find in a CI log. The ratchet runs the tests with the dot
reporter instead: a passing `npm run check` is now **109 lines**, and a failure still prints the
test's name, the assertion and its location. `npm test`, for running the suite by hand, keeps TAP.

### Round 5 — F1, climbing the ratchet where the defects are

Raising the figure by testing whatever is easiest would satisfy the ratchet and miss the point.
The question was where inside App the defects actually land, and git's hunk headers could not
say - they name only the outermost function, so every one of 405 changed hunks read "inside
App". Instead, each fix commit's version of App was taken from history and every changed line
mapped to the definition directly inside App that encloses it:

| definition inside App | fix commits, all history | last 45 days |
|---|---|---|
| **`startDraw` / `onDraw` / `stopDraw`** | **21** | **11** |
| `restore` (opening a project) | 10 | 3 |
| `paintFrame` | 8 | 5 |

The draw handlers are the largest cluster - and the palm-on-the-glass bug fixed this month (#361)
was in exactly two of them. `startDraw` turned out to be a chain of early returns whose *order*
is the behaviour, each rule recorded only as a comment beside its `if`: panning before the
eyedropper, the eyedropper before a path, a path before the layer is even resolved, a selection
before any tool.

**Change.** The decision moved to `src/core/pressPlan.ts` as a pure function, `planPress`, and
`startDraw` keeps only the effects. Tests first, one per rule of the order (10). Behaviour is
unchanged, with one line dropped deliberately: the old code set `gesture.target` just before
returning for a press during text editing. Every reader of `gesture.target` is a stroke commit,
which only runs after a press that took a route - and that path sets it afresh - so the line had
no effect.

**The ratchet's own bug, found by using it.** The first run after the extraction showed the
figure *falling*, to 50.71%: the new module was not counted at all. `git ls-files` lists only
what is in the index, so a file not yet added was invisible - a new untested file would pass
locally and fail in CI. `architecture-index.mjs` had the same flaw. Both now list untracked files
too. A gate built in round 4 was wrong, and it took a real round of work to show it.

**Effect.**

| | before | after |
|---|---|---|
| src/ line coverage | 50.72% | **50.86%** (baseline raised) |
| rules of the press order under test | 0 | 10 |

A small move in the figure, and that is the honest size of it: the decision is 69 lines. What it
buys is out of proportion to its size - the most-fixed logic in the app is now the best-tested.
