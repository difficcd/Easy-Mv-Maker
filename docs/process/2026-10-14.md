# Process cycle 1 — 2026-10-14

The first pass through Measure → Analyze → Change. It starts from a written review of how this
project is developed, done for a software engineering course: it identified the process as
incremental development run on XP practices, checked it against the ten XP practices, and closed
with a risk plan and five steps to take. The review's own ordering was that **the measurement
baseline comes first** - it is the cheapest step and the one every other step is judged by - so
that is where this cycle began, and the changes were chosen from what the numbers showed rather
than from the list.

Raw numbers: [`2026-10-14.baseline.json`](2026-10-14.baseline.json), produced by
`node scripts/process-metrics.mjs --json` (all history and `--since 30`).

### Corrections made before the numbers were trusted

The first run gave a defect escape rate of 48.5%. Three things were wrong with how it was being
read, and each moved a number:

- **55 PR titles were prose** ("hooks/ in TypeScript"), so they had no `feat:`/`fix:` prefix and
  counted as neither. Most were the TypeScript migration - refactors - and leaving them out
  shrank the denominator. Classifying a prefix-less PR by its commits, which rebase-merge puts on
  main as written, took the rate to 43.2%.
- **Renames split one file's history.** `App.jsx` and `App.tsx` are the same component; counted
  apart, the hotspot list understated it.
- **The translation tables ranked as hotspots** because every fix that changes a UI string adds
  its translations. They are left out, as is CSS.

And one indicator was redefined: "a fix touching a file another fix touched that week" read 77
because nearly every change wires through App. An indicator that is always high cannot be
watched, so App is excluded from the overlap; it reads 43.

## 2. Analyze

**CI says yes, and defects ship anyway.** The pass ratio is 97-99.7% while nearly one fix lands
for every two changes. The review put this down to CI checking syntax rather than meaning; the
numbers agree, with one refinement - CI does run 1,300 unit tests, so the issue is not that it
only checks syntax but that the tests do not cover where the defects actually land.

**Where they land is one file.** App took 63 fix-touches, against 11 for the next. This is the
"super component" the review named as the cost of building without design, now with a count. The
second hotspot, `canvasUtils`, no longer exists - it was split up in #290 - which is some evidence
the refactoring the review credited is the right remedy.

**Test-after, measured.** 56% of all fixes landed without touching a test. That has improved -
40% over the last month - but a fix without a test is the clearest case of the test-after
development the review blamed, because nothing stops the same defect returning.

**CI enforced four of its ten gates.** Found while wiring in the first change below. `ci.yml`
said it existed to run `npm run check` on every push, and then listed the steps by hand - type
check, tests, hook baseline, build. Every gate added locally since (helper index, unreachable
names, unused imports, stroke writes, native dialogs, i18n) bound only on a machine where someone
remembered to run it. The review's statement that the XP rule "every build must pass the tests"
was already implemented in CI was true for four tenths of it. CONTRIBUTING.md said "`npm run
check` is what CI runs", and was wrong.

**The documents drift, and by how much.** `ARCHITECTURE.md` - the file whose own title says to
read it before editing - did not name 44 of the 152 files under `src/`, 29%. The `export/` folder
had no section at all; App's stated size was 2,100 lines against 2,198. A loose search (the bare
word, not the filename) found only 34 missing, because "zip" and "camera" appear in prose without
the files ever being named. The review's diagnosis was that keeping documents current is never
the cheapest next step in incremental development, which is why the cure has to be a check rather
than a resolution.

**Some of the measurements cannot be trusted yet.**
- Only 11 of the 73 fixes had a bug-labelled issue, so MTTR describes about 15% of defects.
- PR lead time is near zero because PRs are opened after the work is done; the issue → close
  figure is the meaningful one, and it is bimodal - most issues close the day they open, and the
  rest wait weeks.
- "Deferred verification" read 0 while #338 was waiting on a device, because nothing recorded the
  wait.

## 4. Not changed this cycle, and why

- **A requirements specification** - the review's first step, derived backwards from what is
  built and then checked by the customer. Its last step is the customer's own, so it is a draft
  to write next rather than something to finish here.
- **Outside feedback** and **DevOps readiness** need a decision and a server respectively; there
  is nothing to measure yet.
- **A testing cadence.** How often deferred checks must be closed is the owner's call. C4 makes
  the backlog countable, so whatever period is chosen can be checked rather than remembered.
- **Labelling every fix with an issue,** which would make MTTR mean something. It is a habit, not
  something a gate can enforce cheaply - flagged here so the next cycle can see whether it took.
